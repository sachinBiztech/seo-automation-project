3. OPENCLAW TELEGRAM SPECIFICS
────────────────────────────────────────────────────────────────────────────────

GROUP CONFIG (in openclaw.json → channels.telegram.groups):
  requireMention: true    Bot only responds when @mentioned in the group
  groupPolicy: "open"     Bot accepts messages from all group members

INLINE BUTTON CALLBACKS:
  - When a user clicks an inline button, Telegram sends a callback_query
  - The callback_data string goes to the bot (format: "action|entity_id")
  - OpenClaw passes this as a TEXT message to the main agent LLM
  - The LLM may hallucinate the action without actually executing it
  - SOLUTION: Use session-bridge.js to detect and handle callbacks directly

IMPORTANT LIMITATION:
  - Telegram only allows ONE active getUpdates poller per bot
  - If you start a second poller, you get: "Conflict: terminated by other getUpdates request"
  - You CANNOT run a parallel Telegram listener alongside OpenClaw gateway
  - SOLUTION: Watch the session JSONL file instead (see section 6)

CALLBACK QUERY TIMEOUT:
  - Telegram callback_query expires in ~30-60 seconds
  - If the LLM takes longer to respond, answerCallbackQuery fails
  - Error: "query is too old and response timeout expired"
  - This does NOT mean the message was lost — it was received, just answered late

4. SOUL.MD — WRITING RELIABLE AGENT INSTRUCTIONS
────────────────────────────────────────────────────────────────────────────────

PROBLEM: gpt-4o-mini reads SOUL.md but hallucinate actions
  - It sees what the expected response should look like
  - It generates that response WITHOUT actually doing the action
  - Example: "✅ Approved. Status updated." — but never called exec

ROOT CAUSE: Conflicting rules
  "Avoid unnecessary exec calls" (general rule) overrides
  "Execute: node approval-bridge.js" (specific instruction)
  The LLM resolves the conflict by skipping the exec

HOW TO WRITE STRONG SOUL.MD INSTRUCTIONS:
  1. Put mandatory actions ABOVE conflicting general rules
  2. Use "MANDATORY", "DO NOT SKIP", "OVERRIDES ALL OTHER RULES"
  3. Explain WHY skipping breaks things (LLMs respond to consequences)
  4. Add "WARNING: If you only reply with text and don't call exec, the file is NEVER updated"
  5. Don't just say "Execute:" — say "Use your exec tool to run:"
  6. Add EXCEPTION notes to general rules: "Avoid exec — EXCEPTION: callbacks always require exec"

LESSON: Never rely on LLM to execute critical state changes.
  Use deterministic scripts (Node.js) triggered by file watchers or webhooks instead.

6. SESSION BRIDGE PATTERN (reliable callback handling)
────────────────────────────────────────────────────────────────────────────────

PROBLEM: LLM agents can't reliably execute code on button clicks
SOLUTION: Watch the session JSONL file, detect callbacks, call scripts directly

HOW IT WORKS:
  1. OpenClaw writes every incoming message to a JSONL session file
  2. session-bridge.js tails that file (polls every 500ms)
  3. When it sees a user message matching "action|entity_id", calls bridge
  4. The LLM still replies (you can't stop it), but the real action already happened

KEY FILES:
  /home/sachin.p/Documents/seo-automation/session-bridge.js   ← the watcher
  /home/sachin.p/Documents/seo-automation/approval-bridge.js  ← writes JSON files

SESSION FILE MAP:
  Read: ~/.openclaw/agents/main/sessions/sessions.json
  Find key: "agent:main:telegram:group:-1003829892114"
  Value: { "sessionFile": "/path/to/uuid.jsonl" }

START THE BRIDGE:
  cd /home/sachin.p/Documents/seo-automation
  node session-bridge.js &

CHECK IT'S WORKING:
  cat outputs/session-bridge.log

APPROVAL STATES (sprint-approval.json):
  pending           → buttons sent, waiting for click
  approved          → TERMINAL — cannot be changed
  rejected          → TERMINAL — cannot be changed
  revise_requested  → NOT terminal — can still approve or reject
  local_file_missing → PDF file not found before sending
  telegram_failed   → could not reach Telegram

7. TOKEN OPTIMIZATION (saving cost + avoiding context limits)
────────────────────────────────────────────────────────────────────────────────

IN CLAUDE CODE (claude.ai/code):

  /compact          Summarize conversation and clear context (use when context
                    is getting large — keeps recent work, drops old detail)

  /clear            Wipe context entirely and start fresh

WHEN TO COMPACT:
  - After completing a major task (pipeline built, feature working)
  - When you see "context approaching limit" warnings
  - Before starting a completely new task in the same session
  - Every ~50-100 exchanges for long sessions

OPENCLAW AGENT TOKEN SETTINGS (openclaw.json):
  contextTokens: 32000          Max tokens per agent context window
  cacheRetention: "short"       How long prompt cache is kept (short/medium/long)
  compaction.mode: "safeguard"  Auto-compact when approaching limit
  compaction.reserveTokensFloor: 8000   Headroom kept for response generation

CONTEXT PRUNING (openclaw.json):
  mode: "cache-ttl"             Prune by time-to-live
  ttl: "1h"                     Old tool results cleared after 1 hour
  keepLastAssistants: 3         Always keep last 3 assistant messages
  softTrimRatio: 0.3            Trim 30% when approaching limit
  hardClearRatio: 0.5           Force-clear 50% at hard limit

PROMPT CACHING:
  - OpenClaw uses prompt caching automatically (saves cost on repeated SOUL.md reads)
  - Prompt cache TTL: ~5 minutes (Anthropic), varies by provider
  - cacheRead tokens cost ~10x less than regular input tokens
  - For long SOUL.md / BOOT.md files, caching gives significant savings

COST-SAVING TIPS:
  - Use claude-haiku for simple data pulls (10x cheaper than opus)
  - Use MOCK mode during development (no real API calls)
  - Use sessions_spawn for subagents (isolated context = smaller windows)
  - Avoid loading large files unnecessarily in agent instructions
  - Use compaction hooks to auto-summarize session history

MODEL COST TIERS (rough guide):
  claude-haiku-4-5     → cheapest, fast, good for data tasks
  claude-sonnet-4-6    → mid-tier, good for analysis + writing
  claude-opus-4-6      → most capable, use for orchestration + strategy only
  gpt-4o-mini          → OpenAI cheapest, used by OpenClaw main agent default

8. DEBUGGING PATTERNS
────────────────────────────────────────────────────────────────────────────────

"Is my agent receiving the message?"
  → openclaw logs | tail -50
  → Look for: "✅ Sent via telegram. Message ID: ..."
  → Look for: "answerCallbackQuery failed" (means callback WAS received but late)

"Did the callback actually update the file?"
  → cat outputs/sprint-approval.json
  → Check "status" field — if still "pending", bridge was never called

"Which session file handled the last message?"
  → cat ~/.openclaw/agents/main/sessions/sessions.json
  → Find the key for your chat (e.g. agent:main:telegram:group:-1003829892114)
  → Read the sessionFile path
  → tail -20 <sessionFile> | grep -o '"role":"[^"]*"'

"What did the agent actually do (not what it said it did)?"
  → Read the session JSONL file
  → Look for "toolCall" entries with "name":"exec" — these are real actions
  → "assistant" entries with only "text" = LLM generated response, no real action

"Why isn't exec being called?"
  → Check SOUL.md for conflicting rules ("Avoid exec" overrides "Execute:")
  → Check exec-approvals.json for allowlist entries
  → Check openclaw exec-policy show for effective policy

"getUpdates conflict error"
  → You have two things trying to poll Telegram simultaneously
  → OpenClaw gateway owns the getUpdates poll
  → You CANNOT run a second getUpdates poller
  → Solution: watch session files instead, or use Telegram webhooks

11. COMMON MISTAKES TO AVOID
────────────────────────────────────────────────────────────────────────────────

❌ Using --file instead of --media for document attachments
   → openclaw message send --media "/path/file.pdf"

❌ Using relative paths in agent .md files
   → Always use: seo-automation/outputs/filename.json (workspace-relative)

❌ Starting a second Telegram poller (getUpdates conflict)
   → OpenClaw owns the poll. Use session file watching instead.

❌ Trusting LLM replies as proof that an action happened
   → "Status updated" in a reply means nothing. Check the actual file.

❌ Using "Execute:" in SOUL.md without saying "use your exec tool"
   → LLM interprets "Execute:" as informational, not as a tool call instruction

❌ Running openclaw run (invalid command)
   → Correct: openclaw agent --message "Run <agent> using /path/to/orchestrator.md"

❌ Forgetting to start session-bridge.js before sending buttons
   → The bridge must be running BEFORE the user clicks a button

❌ Forgetting to reset sprint-approval.json before re-testing
   → Approved/Rejected are terminal states — bridge will skip further clicks
